# Nginx 백엔드 연결 재사용 변경 결과

측정일: 2026-11-12 (한국 시간)

## 결과

변경 전에는 무대기 캐시 검색의 10명 단계에서 **55,640건의 HTTP 502**가 발생했다. 변경 후에는 같은 조건의 1·10·30·100명 캐시 검색 **911,758건이 모두 HTTP 200**으로 완료됐다. 캐시·콜드 캐시·Redis 장애 및 복구를 포함한 변경 후 18개 시나리오도 모두 기대 조건을 만족했다.

별도의 프록시 회귀 테스트에서는 순차 요청 20건이 사용하는 백엔드 TCP 연결이 **20개에서 1개**로 줄었다. 다른 IP로 재생성한 백엔드에도 프론트엔드 재시작 없이 연결됐다.

## 변경 내용

`front/nginx.conf`의 변수 기반 `proxy_pass`를 이름 있는 `virter_backend` upstream으로 바꿨다. 워커별 유휴 연결을 최대 32개 재사용하고, HTTP/1.1과 비어 있는 `Connection` 헤더를 명시했다. `/api` 접두사 제거와 기존 전달 헤더는 유지했다.

upstream에 공유 `zone`과 `server backend:8080 resolve`를 설정하고 Docker DNS를 HTTP 범위에서 조회한다. 백엔드 컨테이너의 IP 변경을 반영하면서 연결을 재사용하기 위한 설정이다. `keepalive 32`는 전체 활성 연결을 32개로 제한하지 않는다.

이번 Nginx 1.30.6에서는 변경 전에도 HTTP/1.1로 전달되는 것을 확인했다. 핵심 변화는 이름 있는 upstream을 통해 연결 재사용 경로를 사용하는 것이다.

부하 도구와 모의 서버 연결용 백엔드 설정은 기존 `perf/search-load-tests` 작업의 stash를 `/tmp/virter-nginx-validation` 작업 공간에 복원해 양쪽에 동일하게 사용했다. 원래 stash는 유지했다. 기존 서비스·대회 데이터·운영 비밀번호를 사용하지 않았으며 실제 Codeforces에는 부하를 보내지 않았다. NGINX Proxy Manager와 TLS 구간은 포함하지 않았다.

## 캐시 적중 지속 부하

성공 RPS는 HTTP 200 건수를 단계 실행 시간으로 나눈 값이다. `TIME_WAIT`는 단계 종료 시 프론트엔드에서 백엔드 8080으로 연결했던 IPv4 소켓 수다.

| 설정 | 가상 사용자 | 전체 요청 | HTTP 200 | HTTP 502 | 성공 RPS | 전체 응답 p95(ms) | TIME_WAIT |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 변경 전 | 1 | 26,551 | 26,551 | 0 | 885.00 | 1.83 | 26,553 |
| 변경 후 | 1 | 71,614 | 71,614 | 0 | 2,387.13 | 0.59 | 157 |
| 변경 전 | 10 | 61,058 | 5,418 | 55,640 | 180.56 | 12.68 | 28,231 |
| 변경 후 | 10 | 277,985 | 277,985 | 0 | 9,266.17 | 1.33 | 607 |
| 변경 후 | 30 | 281,382 | 281,382 | 0 | 9,379.09 | 3.94 | 620 |
| 변경 후 | 100 | 280,777 | 280,777 | 0 | 9,357.99 | 16.55 | 355 |

모든 캐시 적중 단계에서 측정 중 `user.status` 호출은 0회였다.

변경 전 10명 단계의 502 비율은 **91.13%**였다. 오류를 포함한 전체 응답 RPS는 2,034.79였으므로 이를 성공 처리량으로 해석하지 않는다. 이 단계에서 검증이 실패해 변경 전 30·100명 및 이후 장애·복구 시나리오는 실행하지 않았다. 변경 전 p95에는 502 응답도 포함되므로 변경 후의 성공 응답 지연과 같은 의미로 비교할 수 없다.

실패 로그에는 다음 오류가 기록됐다.

```text
connect() to ...:8080 failed (99: Address not available) while connecting to upstream
```

실패 시 `TIME_WAIT` 28,231개는 임시 포트 범위의 크기 28,232개에 근접했다. 연결 재사용 후 같은 10명 단계의 소켓은 607개로 줄었고 502가 사라졌다. 순차 요청의 실제 연결 수 감소까지 함께 확인했으므로, 이번 조건에서는 프록시의 새 연결 누적으로 인한 임시 포트 소모가 주요 원인이었음을 뒷받침한다.

각 단계는 한 프로젝트에서 순서대로 실행했으므로 `TIME_WAIT`에는 이전 단계의 연결도 남아 있을 수 있다. 표의 값은 해당 단계에서 생성된 소켓 수나 실행 중 최고값을 뜻하지 않는다.

## 기능과 복구 회귀 검증

Docker 기반 회귀 테스트는 다음을 확인했다.

- `nginx -t`, `/api/search` → `/search`, 반복 `handle` 쿼리 유지.
- `Host`, `X-Forwarded-For`, 백엔드 HTTP/1.1 전달 유지.
- 순차 요청 20건의 백엔드 TCP 포트: 변경 전 20개로 실패, 변경 후 1개로 통과.
- 기존 백엔드 IP를 별도 컨테이너에 예약해 재사용을 막은 뒤 다른 IP로 교체. 프론트엔드 컨테이너 ID가 같은 상태에서 약 **10.56초** 후 새 백엔드로 연결.

프론트엔드의 기존 테스트 18개, 타입 검사(오류·경고 0개), 정적 빌드도 통과했다.

실제 Spring 백엔드와 Redis를 포함한 변경 후 부하에서도 다음 동작을 확인했다.

| 시나리오 | 검증 결과 |
| --- | --- |
| 같은 핸들의 콜드 캐시 | 1·10·30·100건 모두 200, 각 묶음의 외부 조회 1회 |
| 서로 다른 핸들의 콜드 캐시 | 1·10·30·100건 모두 200, 핸들별 외부 조회 1회 |
| Redis 장애 | 각 묶음에서 직접 조회 1건만 200, 나머지는 `SEARCH_TEMPORARILY_UNAVAILABLE`과 503; 최대 외부 동시 조회 1건 |
| Redis 복구 | 시작 명령부터 검색 및 캐시 저장 확인까지 약 5.82초, 백엔드 재생성 없이 복구 |
| 복구 후 캐시 적중 30건 | 모두 200, 외부 조회 0회 |
| 복구 후 같은 콜드 핸들 30건 | 모두 200, 외부 조회 1회 |

Redis 복구 시간에는 컨테이너 기동·재연결·검증용 조회가 포함된다. DNS 검증의 약 10.56초 역시 해당 실행에서 관측한 값이며, `valid=10s`가 복구 시간 상한을 보장하는 것은 아니다.

## 판정과 한계

변경 전 재현된 프록시 연결 고갈이 이번 무대기 부하 조건에서는 개선됐으며, 요청 전달과 DNS 주소 변경 대응도 유지됐다. Nginx 1.27.3 이상이 필요한 설정이며 실제 검증 버전은 1.30.6이다.

단일 로컬 호스트에서 소량의 합성 데이터를 사용해 한 번씩 측정했다. 부하 생성기와 모의 서버도 같은 호스트를 공유하므로 최대 운영 수용량이나 다른 사양의 성능을 보장하지 않는다. 전체 NPM·TLS 경로, 장시간 부하, 다중 백엔드 인스턴스는 이번 검증에 포함하지 않았다. 서로 다른 핸들의 실제 Codeforces API 전역 호출 제한은 후속 작업으로 남아 있다.
