# 검색 API 로컬 부하 검증 결과

작성일: 2026-11-11 · 측정일: 2026-11-10 (한국 시간)

## 결과 요약

요청 간격을 둔 기본 검증은 **18개 시나리오 모두 통과**했다. 캐시 적중 시 제출 기록을 재조회하지 않았고, 같은 핸들의 동시 최초 조회는 외부 호출 1회를 공유했다. Redis 중단 시 백엔드 인스턴스의 직접 조회는 동시에 1건으로 제한됐으며, Redis 재시작 후 캐시 저장·조회를 다시 사용할 수 있었다.

별도로 실행한 **무대기 연속 요청 검증은 실패**했다. Nginx가 백엔드에 연결하는 구간에서 `Address not available` 오류와 HTTP 502가 발생했다. 기본 검증 통과는 이 문제의 해결이나 운영 서버 최대 처리량을 의미하지 않는다.

이 보고서는 **2026-11-10의 연결 재사용 개선 전 측정**을 보존한다. 이후 Nginx 설정을 개선했으며, 2026-11-12의 [변경 전후 비교](../nginx/REPORT.md)에서는 무대기 조건의 18개 시나리오도 통과했다. 현재 부하 도구는 개선된 `front/nginx.conf`를 사용하므로 아래의 과거 502 발생이 현재 실행의 기대 결과는 아니다.

## 측정 환경과 방법

| 항목 | 조건 |

실제 Codeforces에는 부하를 보내지 않았다. NGINX Proxy Manager·TLS와 브라우저 렌더링은 측정 경로에 포함하지 않았다. 컨테이너 이미지 태그는 실행 설정 기준이며 이미지 digest는 원본 보고서에 기록하지 않았다.

기본 검증의 캐시 적중 단계는 **가상 사용자 1·10·30·100명**으로 각각 약 30초간 실행했다. 각 사용자는 응답을 받은 뒤 **250ms 대기**했다. 이 숫자는 항상 처리 중인 HTTP 요청 수를 의미하지 않는다. 콜드 캐시 검증은 지정한 수의 요청을 한 번에 보내는 방식이다.

지연은 클라이언트의 요청 시작부터 응답 본문 처리까지 측정하며, 사용자 대기 시간은 제외한다. p95는 측정 표본을 정렬한 뒤 95% 위치의 값을 택한다. 지속 요청의 RPS는 대기 시간을 포함한 단계 전체 시간으로 계산한다.

## 3. Redis 중단과 복구

Redis 컨테이너를 중단한 뒤 선행 검색이 모의 API에 진입한 것을 확인하고 나머지 요청을 보냈다. 따라서 아래 결과는 선행 직접 조회가 진행 중인 상태의 추가 요청 제한을 검증한 것이다.

| 요청 수 | HTTP 200 | HTTP 503 | p50(ms) | p95(ms) | 최대(ms) | API 호출 / 최대 동시 호출 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 1 | 0 | 7,008.04 | 7,008.04 | 7,008.04 | 1 / 1 |
| 10 | 1 | 9 | 2,015.72 | 7,006.05 | 7,006.05 | 1 / 1 |
| 30 | 1 | 29 | 2,012.36 | 2,013.69 | 7,005.45 | 1 / 1 |
| 100 | 1 | 99 | 2,019.19 | 2,024.42 | 7,005.46 | 1 / 1 |

503 응답의 오류 코드는 모두 `SEARCH_TEMPORARILY_UNAVAILABLE`이었다. 예상된 거절 응답이므로 이 시나리오에서는 검증 성공으로 판정했다. 모든 요청이 성공했다는 뜻은 아니다.

직접 조회 요청은 약 7초, 초과 요청은 약 2초 후 응답했다. Redis 명령 타임아웃 2초와 모의 API 지연 5초를 둔 조건에 부합하지만, 각 지연 원인을 별도 추적으로 분해한 값은 아니다. 초과 요청도 Redis 접근 실패를 확인한 뒤 거절되므로 즉시 503을 반환하지는 않았다.

Redis 시작 명령부터 검색 성공 및 캐시 저장을 확인하기까지 **5.68초**가 걸렸다. 이 시간에는 컨테이너 기동, 연결 재시도와 검증용 API 조회가 포함된다. Redis 자체의 기동 시간만 측정한 값은 아니다. 백엔드 컨테이너 ID가 같은지 확인했으며, 테스트 중 백엔드 재시작 명령은 실행하지 않았다.

| 복구 후 검증 | 동시 요청 | HTTP 200 | p95(ms) | 제출 기록 API 호출 |
| --- | ---: | ---: | ---: | ---: |
| 준비된 캐시 재사용 | 30 | 30 | 6.79 | 0 |
| 같은 핸들의 최초 조회 | 30 | 30 | 1,020.05 | 1 |

복구 후 캐시 적중 30건은 약 8ms 동안 한 번 실행한 짧은 묶음이다. 원본에 기록된 3,750 RPS를 지속 처리 성능으로 해석하지 않는다.

## 4. 자원 사용과 Redis 명령량

기본 검증 전체에서 수집한 `docker stats` 원본 680개 표본을 집계했다. 단계 사이와 복구 과정의 표본도 포함하며, 시나리오별 최고값이나 운영에 필요한 최소 사양을 뜻하지 않는다.

| 컨테이너 | 표본 수 | 최대 CPU(%) | 최대 관측 메모리 |
| --- | ---: | ---: | ---: |
| 백엔드 | 340 | 94.64 | 553.80MiB |
| Redis | 340 | 10.32 | 12.89MiB |

CPU는 Docker가 출력한 값으로, 일반적인 Linux Docker 기준 약 100%가 논리 CPU 한 개의 사용량에 해당한다. 메모리는 `docker stats`의 컨테이너 사용량이며 JVM 힙이나 Redis 데이터 크기만을 나타내지 않는다. 표본 사이의 순간 최고 사용량은 놓쳤을 수 있다.

캐시 적중 100명 단계의 Redis 명령 증가량은 **35,894회**였다. 같은 핸들의 콜드 캐시 100건에서는 **3,285회**, 서로 다른 핸들 100건에서는 **1,404회**였다. 같은 핸들의 대기 요청이 100ms마다 캐시와 락을 확인하는 구조의 비용을 보여주지만, 명령량에는 측정용 명령·헬스체크·Lua 내부 명령도 포함되므로 사용자 요청 수와 일대일로 대응하지 않는다.

## 5. 무대기 실행에서 발견한 Nginx 오류

응답 후 대기 없이 다음 요청을 보내는 별도 실행에서는 다음 결과가 나왔다. 각 단계는 같은 테스트 프로젝트에서 순서대로 실행했으며, 단계 사이에 연결 상태를 초기화하지 않았다.

| 가상 사용자 | 전체 요청 | HTTP 200 | HTTP 502 | 전체 응답 RPS | 제출 기록 API 호출 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 26,301 | 26,301 | 0 | 876.67 | 0 |
| 10 | 53,823 | 1,926 | 51,897 | 1,793.86 | 0 |

10명 단계의 502 비율은 **96.42%**였다. 전체 응답 약 1,794 RPS에는 오류가 포함되며 성공 응답은 약 **64.19 RPS**였다. 이 실행은 해당 단계에서 실패로 중단돼 이후 30·100명 및 Redis 장애·복구 단계는 실행하지 않았다.

실제 Nginx 로그에는 다음 오류가 기록됐다.

```text
connect() to 172.21.0.4:8080 failed (99: Address not available) while connecting to upstream
```

오류가 발생한 위치는 프론트엔드 Nginx → 백엔드 연결 구간이다. 11월 10일 측정 당시 프록시 설정에는 업스트림 연결 풀을 통한 재사용 설정이 없었고, 기본 검증에서도 한 단계 종료 시 백엔드 방향 IPv4 `TIME_WAIT` 소켓이 최대 **15,545개** 관측됐다. 연결 생성 누적으로 인한 임시 포트 고갈을 유력한 원인으로 판단했다.

다만 11월 10일 실패 실행 당시의 소켓 수와 임시 포트 범위는 수집하지 않았다. 따라서 이 실행만으로 정확한 고갈 임계값이나 원인을 확정하지 않았고, 당시에는 Nginx 설정 변경 전후 비교도 수행하지 않은 상태였다. 사용자별 250ms 간격은 기능 검증을 계속하기 위해 추가한 조건이며 이 문제의 해결책으로 판정하지 않는다. 후속 비교의 소켓 수와 연결 재사용 검증은 [Nginx 변경 결과](../nginx/REPORT.md)를 따른다.

모든 시나리오는 단일 실행이며 반복 측정에 따른 신뢰구간은 구하지 않았다. 실제 대규모 제출 기록, 다중 백엔드 인스턴스, 장시간 실행, 여러 핸들을 포함한 단일 검색, 실제 Codeforces 지연·오류·호출 제한은 검증하지 않았다. 부하 생성기와 모의 서버도 같은 호스트를 공유한다. 이 결과를 AWS T3 micro 등 다른 사양의 수용량으로 환산하지 않는다.

## 재현과 근거 파일

실행 방법과 강제 중단 시 정리 방법은 [부하 검증 가이드](README.md)를 따른다.

아래 명령은 현재 Nginx 설정으로 실행한다. 11월 10일의 개선 전 설정과 수치를 그대로 재현하는 명령은 아니며, 개선 전후 설정 및 비교 근거는 [Nginx 보고서](../nginx/REPORT.md#근거-파일과-재현)에 보관한다.

```bash
# 기본 검증: 단계별 30초, 응답 후 250ms 대기
node tests/load/run.mjs

# 무대기 연속 요청: 개선된 Nginx 설정으로 검증
LOAD_THINK_MS=0 node tests/load/run.mjs
```

아래 파일은 측정 당시 임시 디렉터리의 원본을 복사한 것이다. 위 수치는 해당 원본을 집계했으며, 현재 Nginx 설정으로 다시 측정한 수치가 아니다.

- [기본 검증 원본 JSON](results/2026-11-10/paced-report.json): 18개 시나리오, `passed: true`, 복구 시간.
- [기본 검증 전체 자원 표본](results/2026-11-10/paced-resources.json): 위 자원 최대값 집계 근거.
- [무대기 실행 원본 JSON](results/2026-11-10/saturation-report.json): 502 발생 및 `passed: false`.
- [무대기 실행 컨테이너 로그](results/2026-11-10/saturation-compose.log): 컨테이너별 마지막 300줄을 수집한 로그이며 전체 실행 로그는 아니다. 저장 시 줄 끝 공백만 제거했다.
